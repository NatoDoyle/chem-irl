Data & Experimentation Pack — Metrics, Taxonomy, Experiments (v1)
0) Scope and stack
? Goal: trustworthy metrics for a web?first MVP with €200/mo cap; run small, safe experiments; inform native build.

? Stack:

? Product DB: Supabase Postgres (+ RLS, Storage, Realtime, pg_cron).

? Event analytics: PostHog Cloud Free (client/server). Mirror critical events into Postgres for truth.

? Dashboards: PostHog + SQL views in Supabase + lightweight Metabase (optional later).

? Jobs: pg_cron (daily 02:00 local) + Supabase Edge Functions for heavier tasks.

? IDs: ULID[1] for user?generated rows (sortable by time), UUIDv4 ok if easier.

2) Metric dictionary (precise definitions)
Identifiers: user_id, match_id, proposal_id, message_id, purchase_id, city_id. All timestamps UTC with a stored user_tz.
? WAU / MAU: distinct user_id with any qualifying event (login, like, match, proposal, confirm, reopen, message, purchase). Rolling 7/30 days.

? Match rate: matches ÷ mutual likes displayed.

? Proposal rate: matches with ?1 proposal within 48h ÷ matches.

? Proposal?Confirm ?24h: proposals receiving a confirm within 24h ÷ proposals.

? Confirm?Show: confirms with bilateral “went” or both attendances via survey ÷ confirms.

? TTD (days): date_confirmed ? actual date_met or survey_time (first “went” mark). Use Kaplan–Meier for censored if needed later; MVP uses medians of completed.

? Reopen?Confirm: reopened proposals confirmed within 48h ÷ reopened.

? Payer share: users with any successful purchase in the last 30 days ÷ MAU.

? ARPPU: total revenue / paying users (30d).

? Refund rate: refunds ÷ charges (credits + subs).

? Report rate: reports per 1k active users; unique reporter rate.

? Moderation SLA hit: % cases resolved within SLA by severity.

7) Experiments framework (simple, safe)
? Assignment: deterministic hash on user_id and experiment_id ? bucket 0..99.
 0–49 = control, 50–99 = variant (50/50). Stickiness = user?level.

? Exposure event: first time user hits the feature gate (e.g., sees proposal composer). Only exposed users are analysed.

? Primary metrics: pre?registered per test (max two). Always include Proposal?Confirm ?24h or Confirmed dates/WAU.
 Guardrails: report rate, moderation SLA, error rate, emails/SMS failure.

? Horizon: 7 days minimum or until reaching min sample size (see §8). No peeking resets decisions; if you peek, use stricter alpha.

? Analysis: difference?in?proportions (Wilson CI) for rates; Mann–Whitney U for medians (TTD). Keep scripts in repo.

? CUPED (optional): use baseline acceptance rate as covariate to reduce variance.

Feature flags: simple experiments table with (experiment_id, enabled, percent, start_at, end_at); gate in API.

8) Power and sample sizing (rules of thumb)
? Binary rates (e.g., proposal?confirm ?24h):

? Baseline p0 = 0.55. Detect ? = +0.05 with ?=0.05, power 0.8 ? ~1,050 exposures per arm.

? Confirmed dates/WAU: baseline 0.15. Detect ? = +0.03 ? ~1,200/arm.

? Medians (TTD): non?parametric; use 1,500+ per arm or run longer.

? If traffic is lower, run sequential but set a max 4?week cap and a minimal effect you care about.


9) KPI SQL (Supabase/Postgres) — examples
Proposal?Confirm ?24h (last 7 days):
WITH props AS (
  SELECT p.proposal_id, p.created_at, c.created_at AS confirm_at
  FROM proposals p
  LEFT JOIN confirms c USING (proposal_id)
  WHERE p.created_at >= now() - interval '7 days'
),
agg AS (
  SELECT COUNT(*) FILTER (WHERE confirm_at IS NOT NULL AND confirm_at <= created_at + interval '24 hours') AS confirmed_24h,
         COUNT(*) AS proposals
  FROM props
)
SELECT confirmed_24h::decimal / NULLIF(proposals,0) AS rate_24h FROM agg;

Confirm?Show (last 30 days):
SELECT COUNT(*) FILTER (WHERE s1.went AND s2.went) ::decimal / NULLIF(COUNT(*),0) AS show_rate
FROM (
  SELECT DISTINCT ON (match_id) match_id
  FROM confirms
  WHERE created_at >= now() - interval '30 days'
) conf
JOIN surveys s1 USING (match_id)
JOIN surveys s2 USING (match_id)
WHERE s1.user_id <> s2.user_id;

Median TTD (days):
WITH dates AS (
  SELECT m.match_id,
         DATE_TRUNC('day', LEAST(s1.created_at, s2.created_at)) AS went_day,
         DATE_TRUNC('day', m.created_at) AS match_day
  FROM matches m
  JOIN surveys s1 USING (match_id)
  JOIN surveys s2 USING (match_id)
  WHERE s1.went AND s2.went
)
SELECT PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY (went_day - match_day)) AS median_ttd
FROM dates;

Payer share & ARPPU (30d):
WITH payers AS (
  SELECT DISTINCT user_id
  FROM purchases
  WHERE created_at >= now() - interval '30 days' AND refunded = false
),
revenue AS (
  SELECT SUM(amount_eur) AS eur
  FROM purchases
  WHERE created_at >= now() - interval '30 days' AND refunded = false
),
active AS (
  SELECT COUNT(DISTINCT user_id) AS mau
  FROM (
    SELECT user_id FROM matches WHERE created_at >= now() - interval '30 days'
    UNION ALL SELECT user_id FROM proposals WHERE created_at >= now() - interval '30 days'
    UNION ALL SELECT user_id FROM confirms WHERE created_at >= now() - interval '30 days'
    UNION ALL SELECT user_id FROM purchases WHERE created_at >= now() - interval '30 days'
  ) u
)
SELECT (SELECT COUNT(*) FROM payers)::decimal / NULLIF(active.mau,0) AS payer_share,
       revenue.eur / GREATEST(1,(SELECT COUNT(*) FROM payers)) AS arppu
FROM active, revenue;

Reopen?Confirm (48h):
WITH ro AS (
  SELECT proposal_id, match_id, created_at AS reopened_at
  FROM proposals
  WHERE status = 'reopened' AND created_at >= now() - interval '30 days'
),
co AS (
  SELECT proposal_id, created_at AS confirm_at FROM confirms
)
SELECT COUNT(*) FILTER (WHERE co.confirm_at <= ro.reopened_at + interval '48 hours') ::decimal / NULLIF(COUNT(*),0) AS reopen_confirm_rate
FROM ro LEFT JOIN co USING (proposal_id);

13) Data privacy & minimisation
? Do not log raw message text or images into events. Store sizes only.

? Redact contact handles pre?confirm. Strip URLs from notes.

? Separate PII (email, phone) into a limited?access schema; audit accesses.

? Pseudonymize exports; rotate S3 signed URLs; use least privilege roles.

? Retain only necessary event fields for KPIs; drop IP after 30 days.


14) QA & data quality
? Event validator: unit tests to assert required props present; run in CI.

? Backfill scripts: for missed events; idempotent.

? Reconciliation: daily compare PostHog counts vs DB tables (±3%).

? Anomaly detection: Z?score on key rates; flag if |Z| > 3.

? Versioning: event schema versions; deprecate with 30?day overlap.


15) Naming & time rules
? UTC in DB; render local via user_tz.

? Use TIMESTAMPTZ; avoid client clock for SLAs.

? Store durations as seconds[2]; compute windows server?side.

? Names: events verb_object (e.g., proposal_sent), tables singular.


16) Rollout ladder for features
1. Internal flag off

2. Dogfood with test accounts

3. 5% city bucket

4. 25%

5. 50% + experiment

6. 100% or rollback

Rollback criteria: error rate > 2%, KPI drop > 5pp on Proposal?Confirm ?24h vs control, report rate > 20/1k WAU.
